# ADR 002：面向验收阶段的黑盒 API 安全测试范围

日期：2026-10-12。

状态：**Proposed／待老师评审**。项目负责人已确定新版定位并批准文档编写；技术细节及试跑参数尚未得到老师批准。

## 1. 背景与问题

原项目主要证明 Agent 自身的越权拦截，示例围绕 IP 和扫描工具，未明确测试人员实际要验收什么。老师提出需求定位问题后，项目需要按“重新明确需求 → 记录设计变更 → 更新验收标准 → 调整代码”的顺序推进。

软件测试人员和验收人员在集成测试及交付前需要检查 API 对匿名用户、对象归属和角色的访问限制，并能复核请求、预期与结果。他们可能不掌握源码，但能够提供接口契约和预期权限矩阵。因此选择黑盒 API 作为首版业务入口。

## 2. 决策与候选工程方案

项目名称为“面向软件验收阶段的黑盒授权安全测试 Agent”。测试方式为黑盒 HTTP JSON API，不要求被测系统源码；首版仅针对本地隔离模拟 API，提供未认证访问、对象级和角色级访问控制检查及合法访问对照。

以下为 **RC1 待评审／试跑选择**：模拟 Bearer Token，测试人员提供接口契约和权限矩阵，只读检查，确定性规则 Planner，非 LLM Controller，最多 8 项检查、90 秒逻辑时间、并发 1。GET、一检查一请求、无自动重试和不跟随重定向是进一步提议，具体口径统一见 [Specification](../brief/P3_specification_v1.0-rc1.md) 第 4 节。

保留 ADR 001 的独立授权原则，V1 使用独立模块和强制执行入口，不宣称物理隔离。Executor 只能经 Controller 派发；Controller 批准跨用户测试请求，不代表 API 应批准跨用户读取，业务判定必须依据权限矩阵和响应证据。

## 3. 替代方案与取舍

| 方案 | 取舍理由 |
| --- | --- |
| 源码静态分析／白盒方案 | 需要源码和语言相关分析，不匹配当前只提供接口的验收入口；留作未来可选补充。 |
| 任意公网扫描／通用渗透 Agent | 授权范围与环境不可控，难以构造稳定课程验收；不纳入 V1。 |
| 只做 Controller 防御演示 | 能说明执行边界，但不能给出 API 认证及访问控制的业务结论；保留为系统安全验收的一部分。 |
| 首版即接入真实 LLM | 增加非确定性和成本，尚不能替代完整契约及判定规则；先完成确定性基础验收。 |
| 首版图形界面／复杂平台 | 增加非核心交付工作；优先配置、执行和证据闭环。 |
| 黑盒、本地模拟、确定性规划 | 输入依赖少，夹具与预期可控制，便于复核和重复实验；接受覆盖范围有限。 |

## 4. 后果、局限与后续评估

- 可以围绕明确用户和业务权限设计 Positive／Negative／Adversarial 验收，关联计划、授权、响应和有限结论。
- 黑盒观察不能解释源码根因，也不能证明所有接口或真实部署安全；矩阵错误、对照缺失或证据不足会限制结论。
- 本地模拟 API 和已知缺陷夹具用于验证方法，不代表对真实产品的安全认证。
- 只读范围不覆盖写操作越权；采用 Bearer Token 不意味着首版覆盖登录、刷新、注销及全部 Token 生命周期。
- 模块和入口约束可验证应用调用路径，但不提供物理隔离；更强隔离另行决策。
- V1 必须记录策略、候选、版本和预算，为固定顺序与基于已有结果的动态选择后续比较提供基础。动态策略不要求 LLM，正式比较尚未执行；是否纳入课程最终必选交付见 OQ-07。

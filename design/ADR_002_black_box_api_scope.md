# ADR 002：面向验收阶段的黑盒 API 安全测试范围

日期：2026-10-12。

当前状态：**Accepted（已由项目负责人确定的黑盒／用户／首版范围及已审核工程口径）**，不表示实现、实验或教师教学批准已完成。新框架及证据方案另见 ADR 003（2026-10-14 负责人确认技术路线为 Accepted）；数字预算仍待试跑与教师冻结。

历史状态记录：首轮写作时为“Proposed／待老师评审”；下列 §1～5 保留首轮设计记录，涉及统一待老师批准、后续比较及未同步文件的历史说法，由 §6 的当前记录承接，不能据历史行推断现行审批。

## 1. 背景与问题

原项目主要证明 Agent 自身的越权拦截，示例围绕 IP 和扫描工具，未明确测试人员实际要验收什么。老师提出需求定位问题后，项目需要按“重新明确需求 → 记录设计变更 → 更新验收标准 → 调整代码”的顺序推进。

软件测试人员和验收人员在集成测试及交付前需要检查 API 对匿名用户、对象归属和角色的访问限制，并能复核请求、预期与结果。他们可能不掌握源码，但能够提供接口契约和预期权限矩阵。因此选择黑盒 API 作为首版业务入口。

## 2. 决策与候选工程方案

项目名称为“面向软件验收阶段的黑盒授权安全测试 Agent”。测试方式为黑盒 HTTP JSON API，不要求被测系统源码；首版仅针对本地隔离模拟 API，提供未认证访问、对象级和角色级访问控制检查及合法访问对照。

以下为 **RC1 待评审／试跑选择**：模拟 Bearer Token，测试人员提供接口契约和权限矩阵，只读检查，确定性规则 Planner，非 LLM Controller，最多 8 项检查、90 秒逻辑时间、并发 1。GET、一检查一请求、无自动重试和不跟随重定向是进一步提议，具体口径统一见 [Specification](../brief/P3_specification_v1.0-rc1.md) 第 4 节。

保留 ADR 001 的独立授权原则，V1 使用独立模块和强制执行入口，不宣称物理隔离。Executor 只能经 Controller 派发；Controller 批准跨用户测试请求，不代表 API 应批准跨用户读取，业务判定必须依据权限矩阵和响应证据。

## 3. 替代方案与取舍

| 方案 | 取舍理由 |
| --- | --- |
| 源码静态分析／白盒方案 | 需要源码和语言相关分析，不匹配当前只提供接口的验收入口；留作未来可选补充。 |
| 任意公网扫描／通用渗透 Agent | 授权范围与环境不可控，难以构造稳定课程验收；不纳入 V1。 |
| 只做 Controller 防御演示 | 能说明执行边界，但不能给出 API 认证及访问控制的业务结论；保留为系统安全验收的一部分。 |
| 首版即接入真实 LLM | 增加非确定性和成本，尚不能替代完整契约及判定规则；先完成确定性基础验收。 |
| 首版图形界面／复杂平台 | 增加非核心交付工作；优先配置、执行和证据闭环。 |
| 黑盒、本地模拟、确定性规划 | 输入依赖少，夹具与预期可控制，便于复核和重复实验；接受覆盖范围有限。 |

## 4. 后果、局限与后续评估

- 可以围绕明确用户和业务权限设计 Positive／Negative／Adversarial 验收，关联计划、授权、响应和有限结论。
- 黑盒观察不能解释源码根因，也不能证明所有接口或真实部署安全；矩阵错误、对照缺失或证据不足会限制结论。
- 本地模拟 API 和已知缺陷夹具用于验证方法，不代表对真实产品的安全认证。
- 只读范围不覆盖写操作越权；采用 Bearer Token 不意味着首版覆盖登录、刷新、注销及全部 Token 生命周期。
- 模块和入口约束可验证应用调用路径，但不提供物理隔离；更强隔离另行决策。
- V1 必须记录策略、候选、版本和预算，为固定顺序与基于已有结果的动态选择后续比较提供基础。动态策略不要求 LLM，正式比较尚未执行；是否纳入课程最终必选交付见 OQ-07。

## 6. 2026-10-12 当前决策承接

### Status

**Accepted：已有明确负责人确认的工程范围**。依据前序确定的黑盒定位及已审核并应用的规格；本次没有替负责人接受新的标准库框架、证据阈值或实验结论。正式课程契约、目录及预算的教师批准／冻结尚未取得记录。

### Context

测试／验收人员在集成测试和交付前有接口契约及预期权限矩阵，可能没有源码，需要可复核的业务权限结论。课程 S3 第 37～46 张要求独立控制、有限证据、预算与策略取舍；没有指定必须用黑盒、白盒或某 API 框架。技术路线属于 B 类，教学契约与执行目录属于 A 类，不能混淆。

### Alternatives

| 方案 | 评价：需求、复杂度、安全、成本、可复现性、维护性 |
| --- | --- |
| 黑盒 HTTP JSON + 本地模拟 | 匹配接口验收、输入依赖少、可控制夹具；只读范围较小，断言依赖矩阵，不能解释源码根因。 |
| 白盒静态／源码分析 | 能关联实现路径和根因；需要源码、语言专用分析与误报复核，当前用户入口不提供这些条件；可后续补充，未被实验证明劣于黑盒。 |
| 黑盒与白盒同时交付 | 证据更丰富；范围和维护负担增加，不是当前最小切片必需。 |
| 通用公网扫描／自由工具 Agent | 目标和副作用难控，不满足当前本地只读范围及授权约束，排除。 |
| 只演示 Controller 拦截 | 实现少，但不能给出 API 业务权限结论，不能代替当前目标。 |

### Decision

首版选黑盒 HTTP JSON、本地隔离模拟身份、三类权限检查及合法对照；确定性规则 Planner、非 LLM Controller 独立授权，Executor 通过强制入口。已审核的 GET／无请求体／不跟随重定向／不自动重试和累计计数／首次规划前计时语义沿用。当前模块分离不宣称物理隔离。

REQ-020 元数据和 REQ-021 固定／动态比较及 ADR 取舍均 MUST：依据课程 P3／E1 任务（S3 37、42、46、73、99），基础闭环后开展，允许固定胜出或“需要更多证据”。不照搬 6／3 数字，不要求真实 LLM；8／90／1 为示例试跑数字，由教师试跑后冻结班级预算。此承接替代首轮“比较是否必选待问”及上一轮 MAY，历史记录仍保留。

### Rationale

先让用户能在受控身份／资源范围复核权限矩阵与响应，减少源码、云服务、GUI 和非确定性依赖；以明确证据支持取舍，避免把高自治误当工程质量。路线选择是负责人决定，不是教师统一批准每个架构细节，也不是实测证明黑盒最优。

### Consequences

可重复夹具和有据结论有利于课程验收；代价是有限覆盖、无法确定实现根因、矩阵出错或对照不足时结论受限、只读不覆盖写授权。必须记录未覆盖和误确认，不把 EXECUTED 等同 PASS。正式测试须教师目录批准加目标所有者／授权负责人许可；工程 Accepted 不能替代实际测试授权或正式评分契约。实验与实现均未在本轮执行。

### Reconsideration

若用户需要根因定位且能够提供合法源码、接口契约不足以判定、只读覆盖无法满足已批准验收，重新评估白盒或混合路线并记录新的 ADR；需增加目标／动作时先走课程及目标授权，不能自动扩权。固定／动态试跑没有同声明目标的质量／成本收益时保留固定；硬安全门失败立即停止。框架／隔离／证据组织及具体实验推荐见 ADR 003 和 [治理登记](../brief/P3_decision_governance.md) C 类，不将未试跑结果写成已证实。

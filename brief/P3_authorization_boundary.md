# P3 授权边界与停止条件

版本：V1.0-RC2 配套草案。日期：2026-10-14。状态：**工程治理修订已由负责人审核；正式目录与班级预算的教师批准／冻结记录未取得**。本文描述必须实现的边界及拟议细节，不证明当前代码已经具备这些能力，也不构成对任何目标的实际测试授权。

需求依据：[Specification](P3_specification_v1.0-rc2.md)，特别是 P3-REQ-002、007～012、015～017。安全不变量沿用 [Problem Frame](P3_problem_frame.md) 的 INV-01～05，不另设冲突版本。

## 1. 授权对象与两层权限

只允许具备目标所有者或其明确委托授权负责人许可的本地隔离模拟 HTTP JSON API、模拟 Bearer Token 身份和只读动作；正式课程运行还必须匹配教师批准目录。项目负责人选技术方案不等于拥有目标授权权。测试人员提供接口契约和预期权限矩阵，授权维护者登记具体许可，Controller 使用可信注册表独立判断；未取得许可不得派发。先纯模拟验证，再开放已批准本地动作。

Controller 判断是否允许发送；API 的业务权限是否正确由响应证据和权限矩阵判断。批准模拟跨用户／跨角色请求，是批准执行负向检查，不能改变 API 本应拒绝的业务规则。

## 2. 授权配置最小内容（拟议契约）

| 配置内容 | 必须约束的信息 |
| --- | --- |
| 标识与来源 | authorization_id、版本、批准者标识、批准范围说明、有效状态及有效期（如配置）。必须关联目标所有者许可及正式课程目录批准记录；缺失必要信息即拒绝启动。 |
| 目标 | 精确 scheme、host、port；仅经确认的本地模拟服务。本轮离线配置仅接受回环 IP 字面量；该校验不代表已批准实际网络目的地。 |
| 请求范围 | 已批准的 endpoint_id、路径模板、HTTP 方法、路径／查询参数名及允许值、允许请求头；首版沿用已审核的 GET／无请求体口径，最终发送仍限获准目录。 |
| 身份与对象 | identity_ref（或明确的 anonymous）、模拟凭据引用、角色、对象 ID 及归属；允许的身份与端点／对象组合须显式列出。 |
| 检查范围 | check_id、检查类型、策略可选择的候选集合；不得自行探测未列出的端点或资源。 |
| 预算 | max_checks=8、logical_timeout_seconds=90、concurrency=1，均为课程示例试跑值，按 C-01 试跑，由教师 A-02 冻结本班预算，未有冻结记录。 |
| 停止控制 | Controller 可读取的撤权信号和授权状态；可信本地机制已由负责人按 B-06／ADR 003 Accepted 确认；本轮验证离线交界，HTTP 取消仍待实现与验证。 |
| 证据设置 | 输出位置、脱敏规则、单条响应记录上限；组织方式已按 B-07 确认，上限按 C-03 试跑，截断须标记；不替代教师评价 Schema。 |

配置由可信入口加载并绑定本次运行。运行中允许撤权，不允许扩大范围；需要扩大时终止原运行，重新批准配置并创建新运行。Planner 不得持有或修改 Controller 的可写政策引用；同进程设计不提供对任意恶意 Python 代码的隔离保证。

## 3. 每次派发前的强制检查

Controller 必须依次验证：意图格式和类型 → 授权有效且未撤权 → 目标与端点 → 方法及只读性质 → 身份、对象和参数组合 → 预算和并发 → 记录授权决定 → 派发。

- 缺字段、未知字段、错误类型、非法枚举、歧义路径或越界参数均拒绝，保存原因；不得仅验证 target 和 tool。
- 执行器只能接受通过该入口的请求；Planner 不直接发送 HTTP，不把原始 Token 放入意图或日志。
- 拟议首版仅允许契约明确无业务写入副作用的 GET。服务端安全日志等运维记录不视为业务写入。
- 不自动跟随重定向，不利用代理改变目标，不解析响应中提供的 URL 作为新目标。无法确认实际目的地址在本地批准范围时拒绝。
- 执行时使用已验证的同一份规范化请求，禁止验证后替换目标、凭据引用或参数。最终撤权／预算检查与派发须串行协调。

## 4. 预算与停止

计数／计时／终态口径沿用负责人已审核的 Specification 第 4 节；8／90／1 仍是 C-01 试跑值，最终班级数字按 A-02 教师冻结。一般实现决策不统一等待教师批准：

- 一项检查最多发送一次请求，对照独立计数；候选集合可超过 8 项，累计已登记检查不得超过 8 项。初始计划超过 8 项即 STOPPED/INVALID_INPUT，不发请求、不裁剪。
- 初始登记仅增加 plan_count；接纳首次校验才增加 attempt_count，即使随后拒绝也计一次；实际派发增加 request_count。同次重复校验不重计，已处理项重复提交只记录拒绝，不自动重试。未登记的畸形或越界提案也必须分配 Controller 侧名额与关联标识，拒绝后不能回收名额。保持 request_count <= attempt_count <= plan_count <= 8。
- RUNNING 中追加与初始计划共用累计额度，不得靠删除、替换、改 ID、重置或拒绝回收名额；基础闭环可先固定策略；完整交付须完成 REQ-021 比较及取舍。累计登记 8 项后的新追加仅记录预算拒绝，不登记、不增加尝试数、不派发，STOPPED/BUDGET_EXHAUSTED。第 8 项在其他条件允许时可正常执行。
- 静态输入／授权预检完成后、首次调用 Planner 前记录 t0 并进入 RUNNING；预检不生成计划、不发请求。初始规划、计划校验／登记、后续规划、授权、HTTP 等待、判定和运行中证据处理都计时；实际运行不暂停或重置 t0。90 秒到点即预算停止，不派发新请求，在途应超时或取消；请求超时不超过剩余预算。最终停止报告可在预算外收尾，但不再发请求。
- Controller 串行处理追加及完成事件：先处理该轮待决追加，再判定完成。已登记检查全部处理结束、无待决追加且无停止条件，才为 COMPLETED；授权拒绝可视为处理结束，但其 API 结论仍 INCONCLUSIVE。最后一项（含第 8 项）在 90 秒前处理完可 COMPLETED，恰到 90 秒则 STOPPED/BUDGET_EXHAUSTED。
- COMPLETED／STOPPED 是不可重开的终态；终态后的追加只记录拒绝，原状态及计数不变，不能自动启动新运行。同一检查点的原因优先顺序为 REVOKED、AUTHORIZATION_INVALID、运行错误、预算；全部条件留痕，时间预算优先于单请求 TIMEOUT，详见 Specification 第 4 节。
- 撤权生效后不得派发新请求；尝试取消在途请求并记录结果。已发送请求不能撤回，不得声称零在途请求。停止后到达的响应可留作附加证据，但不得据此将该未完成检查改为 PASS。
- 仅在满足 RC2 第 4 节第 9 项全部条件的无价值重复规划／继续循环中使用 STOPPED/NO_NEW_EVIDENCE；一次未发现漏洞不能触发停止。尚有有价值的批准未执行检查、必要合法对照或在途结果时不得据此误停；全部计划正常处理完仍为 COMPLETED，撤权／预算等停止规则优先且不放宽。
- 授权失效、预算耗尽、撤权、无法可靠保存审计记录或运行时异常都进入停止路径，不自动扩大授权或重新启动。具体条件和原因码以 Specification 第 7 节为准。

## 5. 停止后的报告

保留停止前已完成用例的有据结论；被拒绝、未派发、超时或证据不足的检查为 INCONCLUSIVE，分别记录原因。报告必须分别列出初始登记数、追加登记数、累计 plan_count、attempt_count、request_count、已处理数（含拒绝）、未完成项、停止原因、t0／经过时间和证据缺口。未登记候选及被拒追加项另列为未覆盖，不混入已检查统计。

运行正常结束不等于所有检查通过；某检查被拒绝也不能证明被测 API 正确拒绝。证据写入失败时停止派发，并通过可用的错误输出说明失败；不能承诺在存储不可用时仍生成完整证据文件。
